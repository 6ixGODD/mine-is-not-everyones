# Plan 07 Independent Review — Four-Agent Installer, Managed State, and Doctor

- **Plan reviewed**: `docs/plan/07-four-agent-installer-managed-state-and-doctor.md`
- **Branch reviewed**: `plan/07-four-agent-installer-managed-state-and-doctor`; HEAD `d252ee1`
- **Accepted `dev` baseline**: `9562474`
- **Method**: re-derived the verdict from the immutable Plan, exact Design references, Git history, source code, and adversarial tests actually executed against the compiled binary and library — the implementation report's claims and the green test suite were treated as evidence to verify, not as conclusions.

## Verdict: **REJECTED**

Three independently confirmed, reproduced (not hypothetical) defects, any one of which is sufficient to reject:

1. **The design's explicit "backs up structured configuration before mutation" / "backups before external configuration changes" requirement is completely unimplemented.** `grep -rn "backup\|snapshot" src/agent_setup/` returns zero matches. A normal, default `mine agent install codex` destructively rewrites the user's `~/.codex/config.toml` through a full parse-into-`toml::Value`/re-serialize round trip (confirmed by reading `install.rs`), which the implementation's own report candidly discloses drops all comments and formatting — with **no backup taken first**, **no opt-in required**, and **no Plan authorization** for this specific data-loss behavior.
2. **A partial/interrupted installation permanently and irrecoverably blocks all future installs for that agent**, reproduced end-to-end against the actual compiled binary: skill-payload files are written to the configuration root before the Agent-specific MCP-config merge step, so a failure at the config-merge step (I triggered one concretely, see below) leaves orphaned, unrecorded files on disk; every subsequent install attempt then fails with `MINE_AGENT_COLLISION` (files exist, no managed-state record proves ownership), with **no force/repair/recovery command anywhere in the CLI**. "Managed state is written last" is not atomicity, exactly as the review brief warned; the report's own framing conflates "no managed-state write on failure" with "safe," which independent testing refutes.
3. **The four environment-variable overrides (`CLAUDE_CONFIG_DIR`, `CODEX_HOME`, `PI_HOME`, `OPENCODE_CONFIG_DIR`) are read from the real process environment unconditionally, even when `--config-root` is explicitly supplied**, confirmed by reading `agent_service::real_env()`/`commands.rs::agent_env()` and reproduced by actually setting `CODEX_HOME` and observing the installer attempt to write to it despite an explicit `--config-root`. This is the direct root cause of finding 2's concrete trigger, and it independently violates the review brief's Gate 8 requirement that installer behavior "must not inherit or fall back to real... `CODEX_HOME`" even when an explicit config root is given.

`SafetyGuard`'s hard filesystem boundary (Gate 2) is, on the other hand, independently verified **sound** — including against a genuine Windows junction, after correcting an initial testing mistake of my own (documented below) — which is why findings 2 and 3 manifest as a *collision/blocked-retry* bug rather than an actual filesystem escape. A green `cargo test` suite (306/306) does not exercise any of these three scenarios, exactly as a green suite failing to substitute for adversarial review would predict.

## Gate 2: Hard filesystem safety boundary

Read `src/agent_setup/safety.rs` in full. `SafetyGuard::ensure_within_root` performs three layers: lexical normalization + root-prefix check (catches `..`/absolute-path tricks before any I/O), canonicalization of the longest existing prefix + root-prefix re-check (catches symlink/junction reparse points, including for targets that do not yet exist beneath an existing symlinked prefix), and a final defense-in-depth walk rejecting any path component that is itself a symlink whose target escapes the root.

**Adversarial tests performed directly against the library, using a real filesystem link** (not the existing test suite, and not a lexical mock):

- Created a genuine Windows junction via `cmd /C mklink /J` (the same reliable technique used elsewhere in this codebase, e.g. `design_backup.rs`'s own junction test) pointing from inside a fresh temp root to a fresh temp directory outside it, and independently confirmed `std::fs::symlink_metadata(&link).file_type().is_symlink()` is `true` (i.e., the junction is real, not merely created-as-a-plain-directory).
- Called `SafetyGuard::ensure_within_root` on a path through that junction, both for a component that does not yet exist beneath it (`skills/foo/SKILL.md` before creating `foo`) and for one that fully exists on the far side (after creating it) — **both correctly rejected** with `MINE_AGENT_PATH_ESCAPE`.
- **Self-correction recorded for transparency**: an initial ad hoc probe of mine appeared to show the guard *accepting* a junction escape; this was a mistake in my own test harness (a `cmd` invocation from a Bash shell that silently failed due to a drive-letter/path-separator mismatch, leaving no real junction at the path I probed, so the "acceptance" reflected an ordinary, non-linked directory, not an actual escape). Repeating the probe with a verified-real junction (`is_symlink() == true`) showed correct rejection. This is disclosed here specifically so the correction is auditable rather than silently discarded.
- `..` traversal (`../../etc/passwd`) and absolute-path escape (`/etc/passwd`) are covered by `safety.rs`'s own unit tests and independently re-run (passing).

**Test-suite gap found (Gate 2/Gate 8 overlap), non-decisive but real**: `tests/agent_setup/safety_tests.rs::install_with_symlink_skill_dir_does_not_escape` is `#[cfg(unix)]`-gated for creating a real symlink; on Windows it falls back to `std::fs::create_dir_all(&link)` — an **ordinary directory, not a junction or any link at all** — with a comment claiming "the kernel guard is covered by unit tests on all platforms," which is false: `safety.rs`'s own `#[cfg(test)]` module contains **no symlink or junction test whatsoever** (only lexical traversal/absolute-path cases, confirmed by reading all four of its tests). On the actual platform this review runs on (Windows), **the committed test suite never once exercises a real link against the installer**, contrary to the review brief's explicit requirement ("Confirm tests exercise real filesystem links rather than only mocked or lexical paths"). The underlying guard is sound (verified directly, above), but the claim that it is test-covered on Windows is not currently true.

**Not exhaustively re-tested given the decisive findings elsewhere**: symlinked intermediate components beyond the single-junction case, case/path-normalization differences, and destination-replacement-between-validation-and-write (TOCTOU) were not independently constructed beyond what's covered above; recommended follow-up for the compensating plan.

## Gate 3: Ownership and uninstall safety

Read `src/agent_setup/uninstall.rs` and `src/agent_setup/managed_state.rs` in full. Ownership derives strictly from `ManagedState` records (`OwnedFile`/`OwnedConfigEntry`, each with a path/pointer and an install-time content hash) — never from filenames or expected destinations, confirmed by the uninstall loop operating record-by-record rather than scanning a directory. Drifted files (hash mismatch) are left in place and reported, not deleted (confirmed by code reading; `content_hash` is a non-cryptographic hash, appropriately documented as sufficient for accidental-drift detection rather than an adversarial security boundary — not a decisive concern for a purely local threat model). No recursive directory deletion exists anywhere in the module (`grep` for `remove_dir_all`/similar broad-deletion calls in `uninstall.rs` shows none; removal is file-by-file/entry-by-entry through `SafetyGuard`). Missing recorded files are treated as already-removed (deterministic, non-fatal). This gate is **sound** as far as independently reviewed, and is not part of the rejection basis.

## Gate 4: Installation transaction and recovery — FAILS (decisive)

The report's claim: *"on failure, never leaves a partially claimed managed installation: payload files are staged and only after verification is the managed state written... A failure during staging aborts before any managed-state write."* This is **true but incomplete**, and the incompleteness is exactly the defect the review brief warned about ("managed state is written last alone is not atomicity").

**Reproduced directly against the compiled binary** (not a unit test, not a mock):

```
$ CODEX_HOME=/tmp/fake_codex_home ./target/debug/mine.exe agent install codex --config-root /tmp/isolated_config_root --format json
{"...":"...","error":{"code":"MINE_AGENT_PATH_ESCAPE", "message":"... C:/Users/.../fake_codex_home\\config.toml ... outside the configuration root ... isolated_config_root ..."}, "ok":false}

$ find /tmp/isolated_config_root -type f
/tmp/isolated_config_root/.agents/skills/mine-arch/SKILL.md
/tmp/isolated_config_root/.agents/skills/mine-arch/references/AGENTS.template.md
... (10 skill files total, fully written)

$ find /tmp/isolated_config_root -name '*.json'
(none — no managed-state record, confirming the report's "no managed-state write on failure" claim)

$ ./target/debug/mine.exe agent install codex --config-root /tmp/isolated_config_root --format json   # retry, this time without the bad env var
{"error":{"code":"MINE_AGENT_COLLISION", "message":"... .agents\\skills\\mine-arch\\SKILL.md ... already exists and is not MINE-owned ..."}, "ok":false}
```

The skill payload (agent-agnostic, written before the Agent-specific MCP-config-merge step) landed on disk in full; the failure occurred at the later config-merge step (triggered here via the environment-variable issue in Gate 8's finding, but the same shape of failure — anything failing between "payload written" and "managed state written," including a crash, a permission error, or a mid-write disk-full condition — produces an identical orphaned state). Because there is no managed-state record, the orphaned files look exactly like unrelated user content to the ownership check (correctly, by design, per Gate 3 — the installer cannot and should not assume they're safe to overwrite). The result: **the install is now permanently blocked** — every subsequent `mine agent install codex` attempt fails with `MINE_AGENT_COLLISION`, and **no command in the CLI provides a repair, force, or cleanup path** (`grep -n "force\|recover\|repair"` across `src/agent_setup/install.rs`/`src/cli/commands.rs`'s agent handlers returns nothing beyond the source comment header).

This directly fails the review brief's explicit tests: *"A failed installation must not leave modified files without trustworthy recovery or ownership evidence"* (it does — no recovery path exists) and *"Confirm repeated install/update remains deterministic after interrupted operations"* (it is deterministic, but deterministically broken forever, not deterministically recoverable).

Other Gate 4 sub-questions, addressed by code reading (not independently reproduced given the above is already decisive): configuration-merge failure and atomic-rename failure both occur before any managed-state write (same category as above — orphaned partial state, no rollback of already-written payload files); two concurrent installers are not specifically guarded against by any lock in `agent_setup` (unlike the execution-graph's `TomlStore::save_with_revision`, there is no analogous lock/revision mechanism here — a genuine, additional gap, though not independently reproduced under real concurrency for this review given time constraints).

## Gate 5: User configuration preservation — FAILS (decisive)

**Codex.** Confirmed by reading `install.rs`'s Codex branch: the existing `config.toml` is parsed into a generic `toml::Value` table, the MCP entry is inserted/merged into it, and the whole table is re-serialized via `toml::to_string` and written back — every single time `mine agent install codex` (or update) runs, not merely on first install. This **is** the destructive rewrite the review brief calls out by name, and it is **not gated behind any opt-in flag** — it is the unconditional default behavior of the ordinary install path. The report discloses the comment-loss consequence candidly (`"the toml crate drops comments on round-trip"`) and offers `agent config codex` as a preview command for manual application, but **a separate command that prints a manual snippet does not excuse the destructive default installation**, exactly as the review brief states, and the Plan document (`docs/plan/07-...md`) contains **no mention of TOML/comment/formatting trade-offs at all** — there is no explicit immutable-Plan authorization for this specific, real data-loss behavior.

**Compounding this**: the design's own explicit requirement — *"`mine agent install`... backs up structured configuration before mutation"* (`distribution.md`) and *"backups before external configuration changes"* (`configuration-security-observability.md`) — is not implemented for **any** of the four Agents, Codex included (`grep -rn "backup\|snapshot" src/agent_setup/ tests/agent_setup/` → no matches, confirmed above). Had a backup existed, the comment-loss would at least be recoverable by the user; instead it is simply gone, with no CLI-provided recovery mechanism (unlike, for example, this repository's own `design_backup.rs`, which the design's "Destructive-operation policy" explicitly models this exact pattern after: verified backup before rewrite).

**Claude Code/OpenCode** use JSON merge (`Map<String, Value>` insertion under a JSON pointer) rather than a full-document reparse — comments are not a JSON concept, so this specific data-loss mode does not apply to them, but the same **absence of any backup step** applies equally to their config mutations.

This is independently, decisively blocking per the review brief's own framing: *"Determine whether normal install/update/uninstall rewrites the user's Codex TOML and destroys comments or formatting. If so, treat this as user-data loss unless the immutable Plan explicitly authorizes it and the operation requires deliberate opt-in."* Confirmed: normal install does rewrite and destroy comments; the Plan does not authorize it; it is not opt-in.

Unicode/mixed-line-ending/malformed-content preservation for the JSON-merge Agents was not independently stress-tested beyond what's implied by the JSON merge approach (JSON serialization is Unicode-safe by construction; comments/formatting are not representable in JSON regardless); not pursued further given the decisive finding above already covers the higher-severity TOML case.

## Gate 6: Managed-state integrity

Read `managed_state.rs`. Schema-versioned (`MANAGED_STATE_SCHEMA_VERSION`), `managed_by` marker validated before use, atomic stage+rename write path (consistent with the repository's established `atomic_write` infrastructure), deterministic JSON (sorted keys per the struct's field order and `serde_json`'s serialization, no raw file contents/secrets recorded — only paths, hashes, versions, timestamps). Foreign/malformed state is rejected rather than silently trusted (confirmed by the `AgentManagedStateInvalid` error path and doctor's `MalformedManagedState` status). Not independently verified for this review: safe migration behavior for a *future* (not-yet-existing) higher schema version, and concurrent-write races on the managed-state file itself (no lock mechanism analogous to the execution graph's was found in `agent_setup`, consistent with Gate 4's concurrency gap noted above). Timestamps (`installed_at`) are recorded but the idempotent no-op path is documented as not rewriting the record at all on an unchanged repeat install, which — if accurate — would make repeated identical installs deterministic; not independently re-verified via a byte-diff given the decisive findings already established elsewhere.

## Gate 7: Doctor truthfulness

Read `src/agent_setup/doctor.rs`. `AgentStatus` covers `AgentNotDetected`, `AgentDetectedMineNotInstalled`, `Healthy`, `MissingFiles`, `DriftedFiles`, `StaleVersion`, `McpRegistrationMissingOrIncorrect`, `MalformedManagedState` — a reasonably complete state set. Confirmed the `Healthy` classification requires **all** of: recorded files present on disk (`vertex_payload_present`), zero drifted files, zero missing files, matching `mine_version`/payload identity, **and** a real check of the on-disk MCP registration content (`mcp_entry_correct`, which reads and compares the actual config file's entry, not merely trusts the managed-state hash) — so doctor cannot report healthy purely from managed-state presence, satisfying the core truthfulness requirement. Not independently verified: explicit duplicate-discovery or permission/path-error statuses (not obviously modeled as distinct enum variants; may fall through to a generic error path) — flagged as a minor gap, not pursued further given time constraints and the already-decisive findings elsewhere.

## Gate 8: Test isolation and authenticity — FAILS (decisive, and the root cause of Gate 4's reproduction)

Confirmed by reading `commands.rs::agent_env()` and `agent_service::real_env()`: **every** invocation of `mine agent install|uninstall|status|config` — including every test in `tests/agent_setup/`, which passes `--config-root <tempdir>` — calls `agent_service::real_env()`, which unconditionally reads the **real process environment variables** `CLAUDE_CONFIG_DIR`, `CODEX_HOME`, `PI_HOME`, `OPENCODE_CONFIG_DIR` into the injected `Env.env` map. Only `env.config_root` itself is subsequently overridden from `--config-root`; the four override keys are left populated from the ambient real environment. `Targets::resolve`'s `Env::dir()` helper returns the override value **verbatim as an absolute path**, bypassing `config_root` entirely, whenever the corresponding key is present.

**Practical consequence, reproduced above (Gate 4)**: if any of these four variables happen to be set in the ambient environment where `mine agent install` runs — a real possibility for any developer, CI runner, or user who has genuinely installed Codex/Pi/etc. and has these variables set in their shell profile — the installer computes at least one Agent's destination from the **real** environment variable's absolute path rather than the supplied `--config-root`. `SafetyGuard`'s write-time chokepoint does prevent the resulting write from landing outside `--config-root` (it errors instead, as shown), which is a meaningful defense-in-depth save, but it also means: (a) `--config-root`'s isolation promise is not actually complete at the `Targets`/`Env` resolution layer, only enforced as a last-resort refusal; (b) this exact mechanism is what produces Gate 4's permanent-collision bug; (c) it directly contradicts the review brief's explicit requirement that installer tests/behavior "must not inherit or fall back to real... `CODEX_HOME`" even under an explicit config root.

The existing `tests/agent_setup/` suite does not catch this because it runs in an environment where none of these four variables happen to be set — the bug is latent, not currently triggered by CI/local test runs, exactly the kind of gap a green suite cannot surface on its own.

**Real Agent configuration locations confirmed untouched** by the full test suite and by this review's own adversarial commands: SHA-256-hashed the full file listing under `~/.claude`, `~/.codex`, `~/.pi`, `~/.config/opencode`, and `~/.agents` before and after running `cargo test --all-targets --all-features` and this review's manual reproduction steps (which deliberately used `/tmp` targets, never the real paths) — identical before and after. The live execution graph was similarly confirmed byte-unchanged across the full test run.

## Disposition

Plan 07's ownership model (Gate 3), doctor truthfulness (Gate 7), and hard filesystem escape boundary (Gate 2, once tested with a genuine link rather than a lexical mock) are sound. However, the plan fails on data-safety and recoverability grounds that the governing design explicitly anticipates and requires: no backup-before-mutation exists anywhere in the module despite two separate, explicit design statements requiring one; a real, reproduced, permanent installation-collision bug results from environment-variable handling that does not respect an explicit `--config-root` override; and the disclosed Codex comment-loss is not an authorized, opt-in trade-off but the unconditional default behavior of an ordinary install. None of this is exercised by the (green) test suite, which is why the review brief's "a green suite is necessary but not sufficient" instruction was decisive here.

A compensating plan should, at minimum: (1) implement the design-mandated configuration backup before any Agent config-file mutation, for all four Agents, with the file retained (not merely a manual-apply preview command); (2) fix `agent_env()`/`real_env()` so an explicit `--config-root` fully suppresses the four real environment-variable overrides (or make the override explicit and opt-in, never ambient-by-default, when a config root is injected); (3) add an explicit repair/force/adopt path for orphaned unowned-looking files left by an interrupted install, or restructure the transaction so payload writes are staged somewhere recoverable/rollback-able until the managed-state commit succeeds; (4) either use a comment-preserving TOML editing approach for Codex (e.g. `toml_edit`, already a transitive dependency of this workspace via other crates) or require explicit, disclosed opt-in before ever touching a user's Codex `config.toml` destructively; (5) add a real Windows-junction unit test to `safety.rs` itself (not only an integration-level, Windows-no-op substitute) so the module's own doc-comment claim of cross-platform coverage is actually true; (6) declare `src/cli/commands.rs` in the plan's own exclusive write paths if it is genuinely expected to need touching, per the precedent Plan 05-1 already established.
