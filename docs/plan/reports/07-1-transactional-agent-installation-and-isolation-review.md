## Verdict: **ACCEPTED**

Plan 07-1 genuinely fixes all three defects that caused Plan 07's rejection, each independently reproduced (not merely read) as fixed:

1. **Mandatory exact-byte backup before mutation** — confirmed present (`src/agent_setup/backup.rs`) and exercised: reproduced a real install against a hand-crafted Codex `config.toml` containing a user comment and unrelated tables/keys; after install, the comment, table, and key were **byte-identical**, a verified backup existed on disk (`.mine/agent-backups/.codex__config.toml.bak`), and repeated installs reuse rather than clobber the existing backup (never-silently-overwritten, verified via `backup_preserves_existing_when_original_changed` and my own re-reading of `backup_before_mutation`'s never-clobber branch).
2. **No permanent installation collision after a partial failure** — reproduced via the real compiled binary with all four real-Agent environment variables poisoned to nonexistent paths **and** an explicit `--config-root`: every one of the four Agents (`claude-code`, `codex`, `pi`, `opencode`) installed cleanly, entirely under the injected root; a subsequent retry of the same install is idempotent (not a collision). The library's `FailPhase` test hooks (used by `tests/agent_setup/transaction_tests.rs`, independently re-run) additionally prove rollback-then-successful-retry at every meaningful transaction phase (`AfterBackup`, `AfterFirstPayload`, `AfterPayload`, `AfterConfig`, `AfterManagedState`, `DuringFinalVerify`) — none of these leave a permanent `MINE_AGENT_COLLISION`.
3. **Complete `--config-root` isolation** — reproduced directly: with `CLAUDE_CONFIG_DIR`, `CODEX_HOME`, `PI_HOME`, `OPENCODE_CONFIG_DIR`, `HOME`, and `USERPROFILE` all poisoned to nonexistent paths in the real process environment, every Agent's install landed exclusively under the explicit `--config-root`; the poisoned directories were confirmed to remain completely empty/nonexistent throughout. Source-level confirmation: `Env::isolated`/`Env::real_env` are two structurally separate constructors (`targets.rs`) that are never mixed; `commands.rs::agent_env` uses `Env::isolated` whenever `--config-root` is present and never partially overrides it with `real_env()`'s map.

Additionally: `SafetyGuard`'s hard filesystem-escape boundary was re-verified sound against a **genuine, freshly created Windows junction** (`mklink /J`), independently confirmed to be a real reparse point via `symlink_metadata().is_symlink()`; ownership/uninstall (drift preserved, no recursive deletion, missing files treated as already-removed) and doctor truthfulness (incomplete-transaction detection takes priority; live MCP entry is actually read and compared, not merely trusted from managed state) are both sound on independent inspection.

`cargo fmt`/`clippy -D warnings -W unsafe-code`/`build`/`test --all-targets --all-features` (321/321), `scripts/sync-plugin-assets.py --check`, `scripts/verify.py`, `mine design validate`, and `mine graph validate` all pass, and the real Agent configuration directories under `HOME`/`USERPROFILE` were confirmed unchanged by this review's own manual reproductions (only pre-existing, unrelated real files present — no MINE-owned content). Per the review brief's framing, this green suite and clean tree are treated as necessary, not sufficient; the acceptance rests on the independent reproductions above.

Two real, disclosed-or-independently-confirmed, **non-blocking** findings are recorded for follow-up (neither reintroduces any of Plan 07's three rejected defects, and neither is reachable through ordinary single-fault usage):

- **`rollback_and_fail` unconditionally discards the pending-transaction record even when `rollback()` itself fails** (e.g., if the backup file used for restore is itself corrupted/unreadable at the moment of rollback — a genuine double-fault scenario, not an ordinary single-point failure). I constructed and ran an adversarial reproduction (a temporary, non-committed test added to `install.rs`, executed, and then reverted via `git checkout --`) that corrupts a real backup file mid-transaction and confirms: `rollback()` correctly returns `Err(AgentBackupFailed { .. })` (hash mismatch), but `rollback_and_fail` calls `let _ = rollback(...)` and then unconditionally `let _ = PendingTransaction::remove(...)` regardless of that error, silently deleting the only recoverability signal while the live config remains in its mutated (not-restored) state. This is a real gap in the "belt and suspenders" recoverability model, but it requires an independent compounding fault (the backup itself becoming corrupted) on top of the already-failing operation being rolled back; it is not one of the three originally-rejected, routinely-triggered defects, and it is not reachable through any ordinary `--config-root`/env-var/interrupted-install scenario I could construct. Recommended follow-up: only remove the pending record when `rollback()` itself returns `Ok(())`; otherwise, keep it and surface an actionable `doctor`/CLI report so a human can inspect the still-corrupted state.
- **The plan's own Work Package 4 (and `src/agent_setup/mod.rs`'s doc comment) claims a "real Windows-junction unit test added in-module" to `safety.rs`; this was not actually done.** `safety.rs`'s own `#[cfg(test)]` module still has exactly the same four tests as the rejected Plan 07 branch (traversal, absolute-escape, inside-path, root-itself) — no symlink/junction test at all, on any platform. `tests/agent_setup/safety_tests.rs::install_with_symlink_skill_dir_does_not_escape` is unchanged too: still `#[cfg(unix)]`-real-symlink / Windows-plain-directory, with the same "the kernel guard is covered by unit tests on all platforms" comment that is not accurate on Windows. This is honestly disclosed as an open limitation in the implementation report itself (`"Windows junction unit test in safety.rs: ... noted; ... a dedicated in-module Windows junction test on non-Windows is a no-op"`), so it is not a hidden defect — but `mod.rs`'s own doc comment inaccurately claims this was completed, which should be corrected. The underlying guard logic itself is independently re-verified sound (see above, genuine junction test performed by this review), so this is a documentation/test-coverage gap, not a safety gap.

A third pre-existing (not newly introduced), disclosed-only-in-passing gap, carried over unchanged from before Plan 07 and outside this compensating plan's declared scope: there is still no lock/concurrency-control mechanism for simultaneous `agent install`/`update`/`uninstall`/recovery operations (unlike the execution graph's `TomlStore::save_with_revision`). Not independently reproduced under real concurrency for this review; recommended as a distinct future follow-up, not blocking here since it was never part of Plan 07-1's declared scope or the three defects being compensated for.

## 2. Mandatory backup before every external configuration mutation

Reproduced directly (not just read): created `.codex/config.toml` with a real user comment (`# my custom codex config`), an unrelated `[model]` table, another comment (`# don't touch this`), and a pre-existing, unrelated `[mcp_servers]` entry; ran `mine agent install codex --config-root <root>` against the real compiled binary. Result: **every** original byte sequence — both comments, the `[model]` table, and the pre-existing `existing = { command = "foo" }` entry — survived unchanged, with only a new `[mcp_servers.mine]` table appended; a verified backup (`.mine/agent-backups/.codex__config.toml.bak`) was created and reported in the structured `InstallOutcome`. Re-running the install is idempotent (reuses/verifies the same backup path rather than creating a duplicate, confirmed by the `backup_reuses_matching_existing`/`backup_preserves_existing_when_original_changed` unit tests and by direct code reading of the never-clobber branch in `backup_before_mutation`).

Claude Code and OpenCode use structured JSON-object merges (`edit_json_mcp`) that preserve unrelated top-level keys and other MCP entries (verified by the `json_merge_preserves_unrelated_keys` unit test and independent code reading); Pi has no MCP configuration to mutate. `restore_from_backup` verifies the backup's content hash before restoring (rejecting a drifted/corrupted backup rather than silently restoring wrong bytes), and independently reproduced restoring exact original bytes after a simulated destructive mutation (`restore_restores_exact_bytes`, re-run).

No secrets are logged: `Backup`'s serialized/reported fields are limited to `original_rel`, `backup_path`, and a non-reversible content hash — never raw bytes (confirmed by reading the `Serialize` derive and the `InstallOutcome`/`BackupRef` result shapes actually returned to the CLI envelope).

## 3. Transactional installation and crash recovery

Traced the real phase order in `install_inner` (`src/agent_setup/install.rs`): recover-any-prior-incomplete-transaction → load managed state / compute plan → **mandatory backup** (before any mutation) → **persist the durable pending-transaction record** (before any payload write) → stage+write skill payload (collision-refused if not proven MINE-owned) → merge structured config → final hash verification → atomic managed-state write → remove pending record only after verification succeeds. This matches the plan's declared phase model and, critically, writes the pending record **before** any external mutation (unlike the rejected Plan 07, where managed state — the only durability signal — was written only at the very end with nothing durable recorded beforehand).

Independently re-ran the `FailPhase`-injected rollback/retry tests (`tests/agent_setup/transaction_tests.rs`) covering `AfterBackup`, `AfterFirstPayload`, `AfterPayload`, `AfterConfig`, `AfterManagedState`, and `DuringFinalVerify` — all pass, and each independently proves: modified configuration is restored to exact original bytes on failure (`codex_config_restored_on_failure`); only the current transaction's created files are removed, not unrelated content; a retry after any of these phases succeeds and installs all 5 skills (`rollback_and_retry`); no permanent `MINE_AGENT_COLLISION` results (`no_permanent_collision_after_failure`); `doctor` truthfully reports `IncompleteTransaction` when a pending record exists (`incomplete_transaction_detected_by_doctor`), ahead of every other status; `detect_and_recover` is independently idempotent and removes only transaction-created orphans (`detect_and_recover_recovers_incomplete`).

**Independent adversarial finding beyond the test suite** (see Verdict section above for full detail): a genuine double-fault (rollback itself failing because the backup file used for restore is corrupted) causes `rollback_and_fail` to still unconditionally discard the pending record, silently losing the recoverability signal while the live config remains mutated. Reproduced with a temporary, uncommitted test that was reverted after confirming the behavior. This is real but narrow (requires an independent compounding fault, not merely the kind of ordinary single-point failure — bad env var, disk-full, process kill — that caused Plan 07's rejection) and is recorded as a non-blocking follow-up, not a rejection basis.

Durability of the pending-transaction record: it is written via the repository's existing `atomic_write` stage+rename infrastructure (confirmed by reading `PendingTransaction::save`), so a crash mid-write of the record itself either leaves the old record or none — not a torn/corrupt record — consistent with the review brief's "written to a file is not sufficient if crash windows can lose or corrupt it" concern for the record's own integrity (as opposed to the separate rollback-failure gap noted above, which is about the record being *correctly written but later wrongly removed*, not about torn writes).

**Concurrency**: no lock exists for simultaneous install/update/recovery operations in `agent_setup` (`grep` for `lock`/`Lock` across the module shows none beyond an unrelated comment). This is a real, disclosed-nowhere-but-also-not-newly-introduced gap (Plan 07 lacked it too, and it was not part of Plan 07-1's declared scope or the three defects it compensates for) — not independently reproduced under real concurrent execution for this review; recorded as a distinct, non-blocking follow-up.

## 4. Complete `--config-root` isolation

Reproduced directly against the compiled binary in a real child-process invocation (not merely a unit test): set `CLAUDE_CONFIG_DIR`, `CODEX_HOME`, `PI_HOME`, `OPENCODE_CONFIG_DIR`, `HOME`, and `USERPROFILE` all to nonexistent paths, then ran `mine agent install <agent> --config-root <isolated-tempdir>` for all four Agents. Result: every one of the four Agents' skill files and (where applicable) MCP config entries were written **exclusively** under the injected `--config-root`; `find`-ing the four poisoned directories afterward showed them still nonexistent/empty; the real `HOME`/`USERPROFILE`-derived Agent directories (independently snapshotted before/after the entire validation run, including the full `cargo test` suite) were confirmed unchanged (only pre-existing, unrelated real files present).

Source-level confirmation: `Env::isolated(root)` constructs an env with a permanently-empty `overrides: HashMap` (by construction — the four override keys are never read from `std::env` in this path) and `isolated: true`; `Env::real_env()` is the only constructor that reads `std::env::var_os` for the four keys, and it is called only when `--config-root` is absent (verified by reading `commands.rs::agent_env`'s `match flag(&flags, "config-root")` branch). These two constructors are never mixed or partially combined anywhere in the reviewed diff.

## 5. Ownership, uninstall, and filesystem safety

- **Ownership**: unchanged from the independently-sound rejected-Plan-07 logic (`managed_state.rs` is byte-identical); removal proceeds strictly record-by-record from `ManagedState`, never inferred from filename similarity.
- **Drifted/user-modified content**: preserved (not deleted) on hash mismatch, confirmed by re-running `uninstall_preserves_drifted` and independent code reading of both the JSON and (reworked, `toml_edit`-based) TOML config-entry removal paths — the TOML removal path now correctly recomputes a JSON-form drift hash from the live `toml_edit` table before deciding to remove, rather than reserializing the whole document as the rejected Plan 07 did.
- **No recursive deletion**: confirmed — `uninstall.rs`'s directory cleanup only removes directories it can prove are now-empty, walking up from a known skills-root boundary, never a broad `remove_dir_all`-style call (`grep` confirms no such call exists anywhere in the module).
- **Missing/partially-removed files**: handled deterministically (moved to the integration-level `tests/agent_setup/uninstall_tests.rs::uninstall_handles_missing_files`, confirmed present and passing — the equivalent unit-level test was dropped in this rework, but the integration-level coverage is a legitimate replacement, not a silent regression, since the code path itself is unchanged from the validated original).
- **Malformed/foreign managed state**: rejected via `AgentManagedStateInvalid`/`doctor`'s `MalformedManagedState` status, unchanged from before.
- **Symlink/traversal/junction escapes**: independently re-verified against a **genuine** Windows junction (see Verdict section) — correctly rejected. The lexical traversal/absolute-escape unit tests in `safety.rs` were also independently re-run and pass.
- **Pending transactions diagnosed truthfully**: `doctor`'s `IncompleteTransaction` status takes priority over every other classification (confirmed by reading `doctor()`'s early-return check before any other diagnostic logic runs).
- **Doctor verifies actual payload hashes and configuration entries**, not just managed-state existence — unchanged sound behavior from the original review, re-confirmed by reading `doctor.rs` in full for this branch.
- **No unrestricted `--force`, arbitrary deletion, arbitrary path, shell, or configuration-replacement surface**: confirmed by grepping `commands.rs`'s agent handlers and `agent_setup/*.rs` for `force`/`Command::new`/arbitrary-path acceptance beyond the declared, guarded `--config-root` flag — none found.
